# 拾刊 V3 产品方案

版本：V3.0 Draft
日期：2026-11-07
状态：工程原型 / 联调中

## 1. 一句话定位

拾刊 V3 是一个面向内容运营团队的微信公众号采集控制台：平台统一管理 Windows 采集节点、微信登录状态、任务调度、文章库和运行监控；每台 Windows 机器运行一个 Agent，通过已登录的微信桌面端执行采集，并把结果回传到平台。

V3 的核心不是“展示一个漂亮的 Demo”，而是把 Agent、服务端、管理端和数据链路做成一个可运营、可排障、可扩展的小型内容采集平台。

## 2. 产品边界与事实约束

V3 不承诺“零人工干预、纯 API、自动获取任何公众号完整历史”。这个目标受微信产品能力、账号风控和访问边界限制。

更准确的产品边界是：

- 对一个账号可正常搜索到的公众号，平台可以下发采集任务。
- 微信登录使用桌面端扫码或已登录会话；登录本身通常需要人工扫码或保持已登录状态。
- 任务执行过程尽量无人值守；遇到验证码、安全提醒、登录失效、账号受限、桌面锁屏等情况需要人工处理。
- 公众号历史列表的完整性取决于微信客户端暴露的内容，不能保证完整历史。
- 不绕过微信安全流程、验证码、付费墙、隐私限制或已删除内容。

因此，V3 的产品叙事应该是“受控的多节点微信内容采集运营平台”，而不是“无限量爬虫”。

## 3. 目标用户与核心场景

| 用户 | 场景 |
| --- | --- |
| 内容运营 | 持续采集指定公众号的新文章，整理选题库和竞品内容库 |
| 市场与品牌监控 | 跟踪品牌、行业、竞品公众号发布节奏和内容变化 |
| 研究/情报团队 | 归档公众号文章，按时间、账号、关键词检索 |
| 技术团队 | 部署 Windows Agent、维护登录态、查看任务失败原因 |

核心用户故事：

1. 管理员在 Windows 机器上安装 Agent，Agent 自动注册到平台。
2. 操作员在平台发起微信登录，使用手机微信扫码登录该机器上的微信桌面端。
3. 操作员输入公众号名称、数量和是否抓正文，创建采集任务。
4. 平台调度在线且已登录微信的 Agent 执行任务。
5. Agent 打开微信、精确搜索公众号、打开历史列表、逐屏提取文章。
6. 平台接收结果，去重入库，并展示任务进度、事件流和文章详情。
7. 运营人员在文章库中检索、预览和导出内容。

## 4. 产品原则

1. **真实数据优先**：管理端不显示假指标、假连接状态、假成功率。没有数据就显示“暂无数据”或“未配置”。
2. **任务可解释**：每个任务都要有状态、事件流、错误码、重试次数和采集来源。
3. **节点清晰**：一个 Agent 对应一台 Windows 机器和一个微信登录态，避免多账号互相抢占。
4. **UI 自动化有边界**：LLM 只负责看屏幕、选动作和复核结果，不生成任意系统命令。
5. **结果幂等**：同一篇文章按规范化 URL 去重，任务重试不造成重复入库。
6. **安全与合规内建**：不绕过登录、验证码、付费内容和平台风控。

## 5. 总体架构

```text
Vue 管理端
    │ REST / JWT
    ▼
Golang 控制台
    │  REST API、任务调度、文章库、用户权限、扫码会话
    │
    ├── SQLite / 后续 PostgreSQL
    │
    │ WebSocket / Agent Protocol
    ▼
Windows Agent
    │ 注册、心跳、任务执行、截图上传、结果回传
    │
    ├── windows-mcp
    ├── 视觉 LLM
    ├── 微信桌面端
    └── 文章列表 / 正文提取
```

V3 继续采用三端架构：

| 组件 | 技术栈 | 职责 |
| --- | --- | --- |
| Platform | Go + chi + SQLite | 用户权限、Agent 注册、任务队列、调度、WebSocket Hub、文章入库、扫码会话 |
| Agent | Python + windows-mcp + 视觉 LLM | 控制微信桌面端，执行搜索、列表读取、正文提取、错误恢复 |
| Admin | Vue 3 + TS + Element Plus | 登录、Dashboard、Agent 管理、任务管理、文章库、设置 |

部署形态：

| 模式 | 说明 |
| --- | --- |
| 单机演示 | Server、Agent、Frontend 在同一台机器，适合联调 |
| 小团队部署 | Server / Frontend 部署在服务器或 Docker，Agent 部署在若干 Windows 机器 |
| 多节点生产 | Server 和数据库独立部署；每台 Windows 机器运行一个 Agent；Agent 通过 HTTPS/WSS 连接平台 |

## 6. 关键业务流程

### 6.1 Agent 接入

1. 在 Windows 机器安装 Python 运行环境和 Agent。
2. 配置平台地址、注册密钥和微信路径。
3. Agent 调用 `POST /agents/register` 注册。
4. 平台返回 Agent ID 和 Agent Token。
5. Agent 保存本地登录凭据，并通过 WebSocket 上报 `agent.hello`。
6. 平台把 Agent 标记为在线，并周期性处理心跳。

### 6.2 微信登录

目标流程：

1. 操作员在 Agent 详情页点击“获取二维码”。
2. 平台创建扫码会话，并通过 WebSocket 下发 `wechat.login.request`。
3. Agent 捕获微信桌面端登录二维码。
4. Agent 通过 WebSocket 上传二维码。
5. 管理端轮询或实时更新二维码。
6. 用户手机扫码，Agent 上报 `scanned`。
7. 用户手机确认，Agent 上报 `confirmed`。
8. 平台更新 Agent 的 `wechat_logged_in` 状态。

当前工程状态：服务端已有扫码会话模型和 API，Agent 尚未完整实现登录二维码请求处理。这是 V3 首个需要补齐的关键链路之一。

### 6.3 采集任务

1. 操作员创建 `fetch_articles` 任务。
2. 请求参数包括公众号名称、数量、时间范围、是否抓正文、优先级和可选指定 Agent。
3. 平台任务进入 SQLite 队列。
4. 调度器选择在线、已登录微信、心跳有效且未满载的 Agent。
5. 平台发送 `task.assigned`，设置租约。
6. Agent 回复 `task.ack`，状态进入 `running`。
7. Agent 上报 `task.progress`。
8. Agent 分批上报 `task.result`。
9. Agent 最终上报 `task.complete`。
10. 平台按 URL 去重入库，并更新任务终态。

### 6.4 微信采集流程

1. Agent 检查微信进程是否运行。
2. 未运行时启动微信，已运行时激活窗口。
3. 判断当前是否处于已登录状态。
4. 在微信搜索框输入完整公众号名称。
5. 从搜索结果中只选择名称精确匹配的公众号。
6. 打开公众号资料或历史文章页。
7. 对当前屏幕截图和 UI 文本做提取。
8. 按需滚动，读取下一批文章。
9. 按公众号、标题、发布时间等字段本地去重。
10. 达到数量、识别列表底部、连续无新增或超过最大滚动屏数后停止。
11. 如果开启正文抓取，打开指定文章并逐屏提取正文。
12. 单篇文章正文失败不阻断整个任务，列表结果仍然回传。

### 6.5 失败与恢复

| 异常 | 处理策略 |
| --- | --- |
| Agent 离线 | 任务租约过期后重新调度 |
| WebSocket 断开 | 指数退避重连，未 ACK 消息重发 |
| 微信未运行 | 自动启动微信 |
| 微信未登录 | 上报登录失败，等待用户重新扫码 |
| 窗口被遮挡 | 尝试激活窗口 |
| 精确账号不存在 | 返回 `ambiguous_account`，不选择相似账号 |
| 单篇文章正文失败 | 保留列表元数据，记录 `detail_error` |
| 连续滚动无新增 | 提前停止，并标记未完整 |
| 任务取消 | Agent 中断当前步骤并上报取消 |

## 8. 技术契约

### 8.1 REST API

REST 是管理端与平台端的主契约，统一返回：

```json
{
  "data": {}
}
```

分页返回：

```json
{
  "data": [],
  "meta": {
    "page": 1,
    "page_size": 20,
    "total": 123
  }
}
```

错误返回：

```json
{
  "error": {
    "code": "invalid_request",
    "message": "human readable message"
  }
}
```

核心接口：

| 分组 | 接口 |
| --- | --- |
| Auth | `POST /auth/login`、`GET /auth/me`、`POST /auth/password` |
| Users | `GET /users`、`POST /users`、`PATCH /users/{id}`、`DELETE /users/{id}` |
| Agents | `GET /agents`、`GET /agents/{id}`、`PATCH /agents/{id}/config`、`DELETE /agents/{id}` |
| Agent Runtime | `GET/POST /agents/{id}/screen`、`GET /agents/{id}/logs` |
| WeChat Login | `POST /agents/{id}/wechat/login`、`GET /agents/{id}/qrcode` |
| Tasks | `POST /tasks`、`GET /tasks`、`GET /tasks/{id}`、`GET /tasks/{id}/events`、`POST /tasks/{id}/cancel` |
| Articles | `GET /articles`、`GET /articles/{id}` |
| Dashboard | `GET /dashboard` |

前端所有请求字段和响应字段必须与服务端契约保持一致。服务端统一使用 snake_case；前端可以在 adapter 中转换，但服务端不接收 camelCase。

### 8.2 Agent WebSocket 协议

Agent 协议必须以服务端协议文档为唯一事实来源。

信封结构：

```json
{
  "version": "1.0",
  "id": "uuid",
  "type": "task.assigned",
  "timestamp": "RFC3339",
  "request_id": "optional uuid",
  "agent_id": "agent uuid",
  "data": {}
}
```

Agent 到平台：

| 消息 | 用途 |
| --- | --- |
| `agent.hello` | 连接初始化、版本、能力、微信状态 |
| `agent.heartbeat` | 保活、负载、任务数 |
| `task.ack` | 确认开始任务 |
| `task.progress` | 上报阶段和百分比 |
| `task.result` | 分批上报文章 |
| `task.complete` | 上报任务成功或失败 |
| `wechat.login.qr` | 上传登录二维码 |
| `wechat.login.status` | 上报扫码/确认/过期状态 |
| `agent.log` | 上报运行日志 |
| `message.ack` | 确认平台消息 |

平台到 Agent：

| 消息 | 用途 |
| --- | --- |
| `server.hello` | 下发服务时间、心跳建议、配置版本 |
| `agent.configure` | 下发配置 |
| `task.assigned` | 派发任务 |
| `task.cancel` | 取消任务 |
| `wechat.login.request` | 请求 Agent 提供二维码 |
| `message.ack` | 确认 Agent 消息 |
| `protocol.error` | 协议或处理错误 |

投递语义：

- `task.assigned` 至少一次。
- Agent 使用 `task_id` 幂等执行。
- 平台使用文章 URL 幂等入库。
- 进度、心跳、结果会延长任务租约。
- 租约过期后任务可重新调度。

### 9.2 阻断端到端联调的问题

这些问题必须在 P0 优先解决：

| 问题 | 影响 |
| --- | --- |
| 服务端发送 `task.assigned`，Agent 只识别 `task.fetch_articles` | 任务无法真正派发到 Agent |
| 服务端 Envelope 使用 `version/id/data`，Agent 使用 `version/message_id/payload` | 双方无法稳定解析消息 |
| Agent 没有发送 `task.complete` | 服务端任务无法进入终态 |
| Agent 的任务结果字段和服务端期望不一致 | 文章可能无法入库或字段丢失 |
| Agent 未处理 `wechat.login.request` | 管理端扫码登录无法闭环 |
| 前端创建任务调用不存在的 `POST /agents/{id}/tasks` | 管理端创建任务必然失败 |
| 前端提交 camelCase payload，服务端要求 `type/priority/agent_id/payload` | 即使路径正确也会创建失败 |
| 前端任务和文章响应缺少完整 adapter | 页面字段可能为空或错乱 |
| 分页接口没有返回 `total`，前端只能估算 | 分页总数不准确 |
| 管理端实时通道是空实现并固定显示“已连接” | 用户看到假状态 |
| 登录页仍显示“Mock 演示环境” | 与真实平台定位冲突 |
| Dashboard / 任务页 / 文章页存在硬编码趋势或比例 | 违反真实数据原则 |
| 设置页保存只是本地延迟，不调用后端 | 概念性设置，不是真实功能 |
| Agent 截图上传缺少鉴权且字段解析链路未验证 | 实时截图无法稳定展示 |
| Agent 操作日志由任务状态推导，不是真实日志 | 排障能力不足 |

### 9.3 安全问题

V3 发布前必须处理：

1. 示例配置或文档中不能包含真实 API Key；如果已提交过，必须立即轮换。
2. JWT Secret、Agent Registration Key、管理员初始密码必须从环境变量注入。
3. 所有平台地址生产环境必须使用 HTTPS/WSS。
4. Agent Token 必须只存哈希，重新注册时轮换。
5. QR 二维码、截图和 Agent 日志是敏感数据，需要权限控制和保留策略。
6. 管理端不能长期预填管理员密码。
7. 所有失败日志不能泄露 token、cookie、完整截图数据或用户隐私。

## 10. 阶段规划

### P0：打通真实端到端链路

目标：从“页面存在”升级到“任务真的能跑通”。

范围：

1. 固定一份 WebSocket 协议，服务端和 Agent 使用同一套 message type、envelope 和字段。
2. Agent 支持接收 `task.assigned`。
3. Agent 发送 `task.ack`、`task.progress`、`task.result`、`task.complete`。
4. 服务端将 Agent payload 转成内部文章模型。
5. 前端创建任务改为 `POST /tasks`，payload 使用服务端契约。
6. 前端增加任务和文章 response adapter。
7. 服务端分页返回真实 `total`。
8. 移除前端实时通道假“已连接”，先改为真实轮询。
9. Dashboard 只展示真实数据。
10. 建立一个可重复执行的端到端验收脚本。

验收标准：

- Agent 注册后保持在线。
- 用户通过 API 或管理端创建任务成功。
- 任务进入 `pending -> assigned -> running -> succeeded`。
- 任务事件流能看到分配、ACK、进度、入库和完成。
- 至少一个真实公众号能返回最新文章并入库。
- 相同任务重复执行不产生重复文章。

### P1：单节点稳定 MVP

目标：一个 Windows Agent 可以稳定执行常见公众号采集。

范围：

1. 修复 WebSocket 长连接稳定性。
2. Agent 支持心跳、重连、消息幂等和结果重发。
3. 补齐微信扫码登录闭环。
4. 实时截图上传链路真实打通。
5. Agent 日志真实上报并持久化。
6. 明确错误码和用户可读提示。
7. 管理端展示任务时间线。
8. 移除登录页 Mock 文案和预填密码。
9. 设置页只保留已实现项。
10. 用同一公众号连续执行 3 次采集做回归。

验收标准：

- Agent 长连接保持 1 小时无异常断开。
- 断网恢复后自动重连，任务能继续或正确重试。
- 未登录时任务快速失败并给出明确原因。
- 扫码登录完成后 Agent 登录态正确更新。
- 任务详情可以解释每一步发生了什么。

### P2：多节点运营

目标：从单机工具升级为小团队可运营平台。

范围：

1. 用户管理界面。
2. Agent 批量注册和健康检查。
3. 多 Agent 负载调度验证。
4. 任务失败原因分类统计。
5. 截图和日志保留策略。
6. 文章 JSON / CSV / Markdown 导出。
7. 文章详情补齐图片、封面和原始链接展示。
8. 平台操作审计。
9. Docker 部署配置修复。
10. 备份与升级说明。

验收标准：

- 2-5 个 Agent 同时在线。
- 任务可以按负载调度。
- 一个 Agent 离线后任务可以转到其他节点或正确重试。
- 管理员可以创建 operator 和 viewer。
- 敏感数据有权限控制和保留策略。

### P3：规模化与产品化

目标：支持更大内容运营团队和外部集成。

范围：

1. `accounts` 公众号档案。
2. 定时采集和增量监控。
3. 单篇 URL 导入。
4. 批量账号任务。
5. OpenAPI / SDK。
6. Webhook 通知。
7. PostgreSQL、Redis、对象存储扩展。
8. Prometheus 指标。
9. 更完整的任务模板和权限模型。
10. 文章内容质量和置信度评估。

验收标准：

- 支持定时任务和失败告警。
- 外部系统可以通过 API 创建任务、查询结果、接收通知。
- 大文章正文和图片不再全部堆在数据库主表。
- 有性能基线和容量评估。

## 11. 关键指标

| 指标 | 定义 | V3 MVP 目标 |
| --- | --- | --- |
| 任务成功率 | `succeeded / 终态任务` | 试点公众号达到 90% |
| Agent 在线率 | 工作时间内心跳有效的比例 | 单节点 99% |
| 重连时间 | WebSocket 断开后恢复时间 | 小于 30 秒 |
| 入库准确率 | 标题、链接、账号、时间与屏幕内容一致 | 抽检不出现明显错配 |
| 重复率 | 同一 URL 重复入库比例 | 0% |
| 无人工任务率 | 除登录/安全提醒外无人值守完成比例 | 记录并逐步提升 |
| 平均采集耗时 | 从任务分配到完成 | 按真实公众号建立基线 |
| 排障时间 | 从失败到定位原因 | 事件流必须能解释失败 |

## 12. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 微信 UI 变化 | 选择器和页面结构失效 | 使用截图 + UI 文本双通道，保留快照，按版本回归 |
| 账号风控 | 登录或采集受限 | 控制频率、限制节点并发、失败立即停止 |
| 历史列表不完整 | 用户误以为平台漏采 | 展示 `complete=false`、停止原因、已扫描屏数 |
| LLM 输出不稳定 | 文章字段错误 | JSON Schema 校验、置信度、抽检、必要时人工复核 |
| 长连接不稳定 | 任务丢失或重复 | 租约、幂等、重连、真实日志 |
| 多账号抢夺桌面焦点 | 任务互相干扰 | 每个 Agent 串行，一台机器一个微信登录态 |
| 截图隐私泄露 | 敏感内容暴露 | 权限控制、短保留期、脱敏、禁止 viewer 查看 |
| API Key 泄露 | 服务被滥用 | 立即轮换，检查仓库历史，密钥只放环境变量 |
| 概念性 UI 误导用户 | 信任受损 | 未实现功能隐藏或标为“未接入” |

## 13. MVP 建议范围

V3 MVP 不追求功能数量，只追求一条真实闭环。

MVP 必须包含：

1. 管理端登录。
2. Agent 注册和在线状态。
3. 微信已登录状态展示。
4. 创建按公众号名称采集文章的任务。
5. 单 Agent 执行任务。
6. 任务状态、进度和事件流。
7. 文章列表和文章详情。
8. URL 去重。
9. 真实 Dashboard 基础指标。
10. 明确的失败提示。

MVP 明确不包含：

1. 定时监控。
2. 单篇 URL 采集。
3. 批量账号管理。
4. 公众号档案。
5. 团队协作和复杂审批。
6. OpenAPI / SDK。
7. 复杂 BI 和推荐。
8. 绕过微信限制的能力。

## 15. 发布定义

### Internal Alpha

满足 P0：一个真实任务可以通过服务端派发到 Agent，结果入库，管理端能看到真实状态。

### MVP

满足 P1：单 Agent 稳定采集，任务可解释，失败原因清晰，核心页面没有假状态。

### Team Beta

满足 P2：多 Agent、权限、导出、日志、截图和部署文档达到小团队使用标准。

### V3.0 Release

满足 P3 前置条件：具备基础扩展能力、可观测性和生产部署指引，且没有已知的假数据展示。
